# Deployment Guide

Architecture: **Web (MVC)** -> **API (ASP.NET Core 8)** -> **ML service (FastAPI)** and **SQL Server**.
Render hosts the first three; it does not host SQL Server, so the database is Azure SQL (or any SQL Server your API can reach).

## 0. Honest status
The Python ML code was run and smoke-tested. The .NET projects, `docker-compose.yml` and `render.yaml` were written
without a .NET SDK or Docker available, so **nothing in the .NET/Docker/Render layer has been compiled or deployed yet**.
Expect to fix a few compile errors on first `dotnet build`; work through Section 1 before deploying.
Real Render URLs only exist after you deploy; Render assigns them (typically `https://<service-name>.onrender.com`).

## 1. Local verification (do this first)
```bash
# 1. train the model on real data (CIC-IDS2017 CSVs in ML/data/CIC-IDS2017/)
cd ML && pip install -r requirements.txt && python train_model.py --dataset cicids2017 --tune
# 2. build both .NET projects, fix any compile errors
cd ../Backend/ZeroDay.Api && dotnet build
cd ../../Frontend/ZeroDay.Web && dotnet build
# 3. full stack in Docker
cd ../../Deployment && cp .env.example .env && bash scripts/generate_secrets.sh   # paste values into .env
bash scripts/local_up.sh        # Web :5000  API :5001/swagger  ML :8000/health
```
Smoke test: register at http://localhost:5000, upload a CIC-IDS2017 CSV on **Detection**, check the dashboard, export a PDF report.

## 2. Database (Azure SQL)
1. Azure portal -> create an **SQL Database** (+ server). Note server name, admin user and password.
2. Networking: allow Render to connect. Render shows its outbound IP ranges for your region on the service **Connect** page; add them as firewall rules (or temporarily "Allow Azure services" while testing).
3. Connection string for `ConnectionStrings__Default`:
   `Server=tcp:<server>.database.windows.net,1433;Database=ZeroDayDb;User ID=<user>;Password=<pwd>;Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;`
4. The API creates all tables on first start (`Database__AutoCreate=true`). Alternatively run `Database/schema.sql` yourself and set it to `false`. Use one method, not both.

## 3. Publish the trained model
Render builds from Git. Either commit `ML/models/zero_day_bundle.joblib` (must be < 100 MB for GitHub), or upload it as a GitHub Release asset and set `MODEL_URL` on the ML service to the asset's download URL (the ML service downloads it on boot).
Re-train => replace the file => redeploy the ML service.

## 4. Deploy on Render
1. Push the whole `ZeroDayAttackFramework/` folder to a GitHub repo **with `render.yaml` at the repo root**.
2. Render dashboard -> **New -> Blueprint** -> pick the repo. Render reads `render.yaml` and proposes 3 services:
   `zeroday-ml` (private), `zeroday-api`, `zeroday-web`.
3. Fill the prompts: `ConnectionStrings__Default`, `Seed__AdminEmail`, `Seed__AdminPassword` (strong, 8+ chars with upper/lower/digit), optional `MODEL_URL`.
   `Jwt__Key` and `ML_API_KEY` are generated by Render; the API reads the ML key and address from the ML service automatically.
4. Click **Apply**. First build takes several minutes (XGBoost/LightGBM wheels, .NET restore).
5. Check: `bash Deployment/scripts/check_health.sh https://zeroday-web.onrender.com https://zeroday-api.onrender.com` (use your real URLs). Expect `200` for both.
6. Open the **zeroday-web** URL, sign in with the seeded admin, create an Analyst via **Register**, run a detection.

Your URLs will be:
- Frontend: the `zeroday-web` service URL shown in the dashboard
- API: the `zeroday-api` service URL (Swagger at `/swagger`)

## 5. Operational notes
- **Instance size:** the ML service loads scikit-learn + XGBoost + LightGBM and scores up to 50,000 rows per request; plan for >= 1 GB RAM. `render.yaml` uses `starter`; check Render's current plans and prices. A free instance sleeps when idle and has no persistent disk, so it is not suitable for the API.
- **Uploads:** the API stores CSVs on a persistent disk (`/data`). Without a disk, files vanish on redeploy and re-analysis of old datasets fails (the database rows remain).
- **Secrets:** never commit `.env`. `Auth__ReturnResetToken` must stay `false` in production; password reset needs an email provider wired into `AuthController.Forgot` before real users rely on it.
- **HTTPS:** terminated by Render. The web cookie uses `SameAsRequest`; forwarded headers are enabled.
- **Cold start:** first request after idle can take 30-60 s; the web client timeout is 300 s for large predictions.

## 6. Troubleshooting
| Symptom | Likely cause |
|---|---|
| API logs "Database not ready" forever | wrong connection string or Azure firewall blocking Render |
| Detection returns 503 "ML service unreachable" | ML service still building, or `Ml__BaseUrl` wrong |
| Detection returns 502 "model not available" | model file missing: commit it or set `MODEL_URL` |
| 401 loop in the web app | `Jwt__Key` changed after login; sign in again |
| PDF export 500 | missing `libfontconfig1` in the API image (already in the Dockerfile) |
